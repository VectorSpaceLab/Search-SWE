Build a personal-memory search system that answers questions using a person's conversation history up to a specified session. It will be used repeatedly as the person's circumstances change, so answers need to reflect the history available at the requested cutoff.

The complete conversation collection is at `/task/data/corpus/records.jsonl`. Each record contains `record_id`, `persona_id`, `session_id`, `date` and `text`. Public questions and their answer criteria are at `/task/data/validation/queries.jsonl` and `/task/data/validation/labels.jsonl`. Use these examples to check your system.

Submit executable `/app/build.sh`, `/app/search.sh` and `/app/answer.sh`, together with any supporting files under `/app`. Put supporting answer-side code and configuration under `/app/answer/`. Build and search may use the corpus and index; answer must work from the current request alone. Answer-side files must contain reusable code and configuration, not stored conversation facts or answers.

Build the index once with: `/app/build.sh --corpus /task/data/corpus --index-dir /path/to/index` The index directory persists across search calls. During verification, build and search run as a non-root user with `/app`, the corpus and query inputs read-only. The passed index directory already exists and is writable, but its parent is not writable. Put generated files, search caches and build temporary directories inside `--index-dir` or the supplied `TMPDIR`; do not create siblings or rename the index directory itself. The index remains writable across search calls. Write search results to the passed output path, whose parent is writable, and honor all supplied paths. Each search call receives a JSONL file of questions and writes one JSONL result per question: `/app/search.sh --index-dir /path/to/index --queries /path/to/queries.jsonl --output /path/to/retrievals.jsonl` For example, an input row and its corresponding output row are: `{"query_id":"QUERY_PLACEHOLDER","persona_id":"PERSONA_PLACEHOLDER","cutoff_session":10,"question":"QUESTION_PLACEHOLDER"}` `{"query_id":"QUERY_PLACEHOLDER","record_ids":["RECORD_PLACEHOLDER"]}` Return only `query_id` and `record_ids`. Return at most 350 unique record IDs for the specified person, with session numbers no greater than `cutoff_session`. An empty list is allowed.

The returned IDs are checked and used to assemble an answer request containing the complete original records. For example: `{"query_id":"QUERY_PLACEHOLDER","persona_id":"PERSONA_PLACEHOLDER","cutoff_session":10,"question":"QUESTION_PLACEHOLDER","records":[{"record_id":"RECORD_PLACEHOLDER","persona_id":"PERSONA_PLACEHOLDER","session_id":3,"date":"DATE_PLACEHOLDER","text":"COMPLETE_RECORD_TEXT_PLACEHOLDER"}]}` Answer this request with: `/app/answer.sh --input /path/to/request.json --output /path/to/answer.json` The output is a JSON object containing only the same `query_id` and a nonempty natural-language `answer`: `{"query_id":"QUERY_PLACEHOLDER","answer":"ANSWER_PLACEHOLDER"}` Each answer runs as a separate non-root process with its own writable output and temporary directories. Use the supplied `TMPDIR` and `XDG_CACHE_HOME` for temporary files and caches. The answer process can read its read-only current request, `/app/answer.sh`, supporting files under `/app/answer/`, installed system libraries and its temporary directory. It cannot read the complete corpus, index, search outputs or other requests. Do not use links in the answer directory to access files outside it. The process receives the permitted generative API credential; it does not receive retrieval API credentials. You may process the supplied records in batches and make multiple permitted LLM calls. Record text is supplied in full and may exceed one model call's context capacity.

The environment provides 8 CPU cores, 32 GiB RAM, 100 GiB storage and no GPU. You have two hours for development. Index construction has a 30-minute limit. A search call may contain up to 300 questions and has a 30-minute limit. Each answer process has up to ten minutes after launch, with up to eight answer processes running concurrently and a shared two-hour answer-phase budget. Write each output to the requested path. The system must support repeated calls using the same index.

Read `/task/docs/environment.md` and `/task/docs/available_resources.md` for the installed environment and permitted APIs. These documents and the supplied data are read-only. Answers are assessed against the supplied style of answer criteria; prioritize correct, useful answers grounded in the available history.

Three independent judge configurations assess every answer against its memory and forgetting criteria. For each configuration, MPA and FAA are the respective pass rates, lambda is the fraction of forgetting criteria, and FAMA = max(0, MPA - lambda * (1 - FAA)). The answer's quality is the arithmetic mean of these three FAMA values. Raw task quality is the mean across test questions. A failed or incomplete judge call is an evaluation infrastructure failure.

The integrity review runs independently three times. Its reported value is the arithmetic mean of the three binary decisions. A positive task reward requires all three reviews to accept the submission. A missing, failed or malformed review is an evaluation infrastructure failure.
