We need a compact CPU passage-search engine that can start from a persisted index and serve top-10 lexical results. Please implement it in Rust, with a fully self-built BM25 index. Retrieval quality must reach our fixed Pyserini reference before improvements in quality, query time and index size earn credit. We also need measurements of startup without query warmup and resident memory so those costs remain visible.

The corpus is at `/task/data/corpus.jsonl.gz`: gzip JSONL containing all 8,841,823 MS MARCO Passage v1 documents, with string `docid`, `text` and additional `title` metadata. Index only `text`; including titles would change the task. IDs are exactly the decimal strings from `0` through `8841822`. `/task/data/warmup.jsonl.gz` provides 54 public DL20 queries with string `query_id` and `query` fields for exercising your engine. They are disjoint from dev by ID and normalized text and are not a scored dev subset. Final evaluation uses all 6,980 standard passage dev queries and positive judgments, which are not supplied to the agent. MS MARCO dataset terms apply.

You have Linux x86_64, Rust 1.85.1, four CPU cores, 16 GiB of container memory including children and page cache, 64 GiB of working storage and a 256-PID container limit. Submitted commands are limited to 1,024 file descriptors and 16 GiB per output file during compilation/indexing; each search diagnostic file is limited to 16 MiB. There is no GPU or network, and your budget is 10,800 seconds. A starter at `/app/submission` deliberately does not implement retrieval. Its Cargo files pin byteorder, flate2, memmap2, rayon, regex, rust-stemmers, serde, serde_json, unicode-normalization, zstd and their generic dependencies, all available offline. Exact pins and further environment details are in the Cargo files and `/task/docs`. You can run `python /task/smoke.py --binary /app/build/release/bm25-search` for an optional three-passage synthetic check; it does not estimate full-dev quality.

Implement the dictionary, inverted postings, term frequencies, document lengths, serialization, BM25 scoring and retrieval yourself in Rust. Generic libraries for stemming, tokenization, compression, parallelism and I/O are allowed. Submitted implementations must not use or wrap existing retrieval/index engines such as Tantivy, Lucene, Anserini or Pyserini, or use prebuilt indexes. Pyserini is used only by the verifier as a reference. You may tune BM25 parameters and text analysis, but do not use neural or learned retrieval, external data, downloads, query-specific answer tables, evaluation detection or manipulation of tests or rewards. Results must derive from the corpus and query and remain identical in cold and warm processes.

Leave your source in `/app/submission`: `Cargo.toml`, `Cargo.lock`, `src/main.rs`, any other `.rs` files under `src/`, and optionally `README.md`. Use `bm25-search` as both package and executable name. The limit is 1,000 regular source files, 10 MiB total and 10 nested directory levels; no symlinks or hard links. Exclude workspaces, custom build scripts, Cargo patches, vendored dependencies, `.cargo` overrides, binaries, indexes and generated data. Keep build products elsewhere with `CARGO_TARGET_DIR=/app/build`. Only `/app/submission` transfers to the separate verifier, which recompiles using `cargo build --release --offline --locked --bin bm25-search -j 4`. Compilation has a 600-second limit and the binary may occupy at most 100 MiB. Only cached generic crates can be used; packages cannot be downloaded during execution.

The verifier creates an empty `/work/index` and invokes `bm25-search index --corpus /task/data/corpus.jsonl.gz --index /work/index --threads 4`. Build all persistent search state there from the corpus within 7,200 seconds. The index must occupy at most 16 GiB of logical file bytes and contain no links, special files or extended attributes, including on its root and subdirectories. Workspace is limited to 64 GiB and 100,000 entries. The index becomes read-only before queries run.

For queries, implement `bm25-search search --index /work/index --threads 4` as a persistent process. Read one JSON object per stdin line, such as `{"query_id":"example","text":"example query"}`, and emit exactly one matching response, such as `{"query_id":"example","results":[{"doc_id":"42","score":1.2}]}`, followed by a newline and a flush. Requests are at most 4,096 UTF-8 bytes; responses including newline are at most 65,536 bytes. Return zero to ten unique valid IDs with finite numeric scores in descending order, using any deterministic tie order. Send diagnostics to stderr, with no ready message or logging on stdout, and exit cleanly within five seconds of stdin EOF. Do not depend on query or label files.

Submitted commands run without grading privileges. Persistent System V IPC, POSIX message queues, kernel keyrings, extended-attribute operations and io_uring are unavailable in all phases; ordinary Rust threads and file-backed memory mapping are supported. During search, the process can read only its compiled executable, immutable index and required system libraries. The corpus, source, compiler caches, hidden data and writable cache directories are unavailable; stdout and stderr remain usable. All retrieval state needed after startup must be in the index or computed from it in RAM.

The reference is Pyserini 1.4.0 with BM25 `k1=0.9`, `b=0.4`, its default English analyzer and top-10 retrieval over text alone. Its index stores neither raw text, positions nor document vectors. Its measured full-dev MRR@10 is exactly `3236243/17589600`, approximately `0.18398616227770956`. A query contributes the inverse rank of its first positively judged hit in the top ten, or zero; average over all 6,980 expected queries. Every query must receive a valid response. Your MRR must reach the exact reference fraction, without rounding it to `0.18` or `0.1840`.

Cold latency uses five fresh processes, each receiving its first query without query warmup. Timing starts before process launch and ends at the first valid response, including runtime startup, index loading and query work. We report all samples, their median and p95. The operating system file cache is not evicted, so this measures process-cold startup rather than guaranteed cold-storage latency. A separate new process runs the 54 disjoint warmup queries, then all dev queries with one request outstanding. The controller measures batch wall time, p50/p95 request latency and throughput as `6980/batch_seconds`. Each request has a 120-second deadline, including cold startup; warmup and the measured batch each have a 3,600-second budget. Sampled cold and warm responses must match exactly, including scores.

Disk is the logical byte sum of every index file, including dictionaries and metadata. We also report build time and sampled peak search-process RSS, which excludes children and unmapped page cache; the 16 GiB container limit includes both. Cold latency, memory, warm p95 and throughput have no separate bonus terms. Throughput is already represented by batch time.

The verifier rebuilds and measures the same pinned reference locally. For valid submissions passing the quality and resource gates, let `M` be MRR, `T` warm batch seconds and `D` index bytes, with corresponding reference values `Mref`, `Tref`, `Dref`. Equal weights give `U=((M/Mref)*(Tref/T)*(Dref/D))^(1/3)` and `reward=U/(1+U)`. Reference-equivalent metrics score 0.5; better quality, less time or less disk improve the score. Missing, invalid, timed-out, over-budget or below-reference submissions receive zero.
