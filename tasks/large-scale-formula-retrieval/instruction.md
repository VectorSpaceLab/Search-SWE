I need to find related mathematical formulas in historical Math Stack Exchange posts so I can inspect the expressions and their original context. Build a search engine that takes a LaTeX formula alone and returns up to 1000 formula instances from the supplied ARQMath v3 collection, ranked to maximize relevance according to official human judgments. The service runs on a small CPU instance: each query must be answered within 50 ms, and the submission plus its prepared index must fit in 34 MiB. Any retrieval approach is acceptable.

Read `/task/docs/environment.md` and `/task/docs/available_resources.md` before starting. The latter describes which external services you may use and when. All supplied inputs are read-only.

The collection is `/task/data/public/formulas.tsv`, a UTF-8 TSV with CSV quoting and header fields `formula_id`, `post_id`, `thread_id`, `type`, `visual_id`, `latex`. IDs are decimal integers, and `type` is `question`, `answer` or `title`. Every row is a retrieval candidate. Post context is in `/task/data/public/posts.sqlite`, whose `posts` table has `post_id INTEGER PRIMARY KEY`, `thread_id INTEGER`, `type TEXT`, `title TEXT`, `body TEXT`, `owner_user_id TEXT` and `creation_date TEXT`; titles and bodies are annotated HTML. `/task/data/public/instance_visual.npy` is a little-endian int32 array mapping instance ID to visual ID, with -1 for unknown or excluded instances. `/task/data/public/corpus.json` gives collection counts.

`/task/data/public/dev/queries.jsonl` contains five development queries as objects with string `query_id` and `latex`, and the adjacent `qrels.tsv` holds their complete judgments in `query_id 0 visual_id relevance` format. Final scoring uses a separate hidden set of assessed queries of the same kind; only the formula is given, without the question title or body. These five queries are the only labeled data you may use. Do not use any other ARQMath topics or relevance judgments, additional datasets, hard-coded answers or precomputed rankings, and do not access or modify the grader.

You have 7200 seconds for development. Development, build and serving each have 2 CPU cores with at most 2 simultaneous CPU execution threads across all your processes, 4 GiB of memory without swap, and 64 GiB of total storage. This storage budget includes public inputs, submission files, indexes, caches and temporary files, with space reserved for diagnostics and filesystem overhead. No GPU is available.

Submit `/app/submission` containing executable `build.sh` and `serve.sh` and any source files they need. Only this directory is transferred to the verifier, and it must contain only regular files and directories. The verifier runs `/app/submission/build.sh --data-dir /task/data/public --index-dir /work/index` with an empty index directory. The build must exit with status zero within 3600 seconds, including all preprocessing, training, encoding, index construction and any external calls. It must generate all corpus-dependent artifacts itself; precomputed corpus artifacts may not be shipped in the submission. Temporary files go under `/work/runtime`, which is also `TMPDIR` and `HOME`. When the build finishes, all of its processes must have exited, and nothing except the files in the index directory may carry state into serving, including shared memory or other IPC objects.

The submission and the completed index together must not exceed 35,651,584 bytes (34 MiB), counting each regular file as the larger of its logical size and allocated blocks, and hardlinks once. The index may contain only regular files and directories. For serving, it is copied as a read-only index into a separate 40 MiB filesystem with 4096 inodes, which also holds filesystem metadata, a reservation equal to the submission size, and every cache or temporary file the service writes.

The verifier then starts `/app/submission/serve.sh` as an unprivileged user (UID 10001), without network access or API credentials, so every file the service needs must be readable by that user. The service exchanges one flushed JSON line on stdout for each JSON line on stdin, writes diagnostics only to stderr, and emits nothing unsolicited. The first request is `{"op":"load","data_dir":"/task/data/public","index_dir":"/serve/index","work_dir":"/serve/runtime"}`. Use these paths; `/serve/runtime` is the only writable location, and the build's `/work` directory is no longer accessible. Reply exactly `{"ok":true}` within 120 seconds of startup. Three development queries follow as a warmup, which must complete within 30 seconds in total. Loading and warmup must not perform corpus preprocessing, training, encoding or index construction.

A query request looks like `{"op":"query","query_id":"opaque-string","latex":"x^2+y^2"}`. Reply with the same `query_id` and zero to 1000 results, for example `{"query_id":"opaque-string","results":[{"formula_id":"123","score":0.5}]}`. Formula IDs are unsigned decimal strings, scores are finite JSON numbers (not booleans), and results are sorted by decreasing score; ties keep their output order. Each response must be at most 1 MiB. A malformed response, wrong query ID, invalid field or score, or more than 1000 results makes the query invalid. An empty result list is valid but earns zero.

Queries arrive one at a time. Each has 50 ms of wall-clock time, from before the request is sent until after the response is received and the process family is suspended, covering all parsing, retrieval, reranking, context reads, cache work and subprocesses. Your processes are paused between queries. If a query times out, crashes or breaks the protocol, it earns zero, and the service is restarted and reloaded before the next query.

Returned instances are mapped to visual IDs. Only the highest-ranked instance of each visual ID is kept, unjudged visual IDs are removed, and judged non-relevant ones stay in the ranking. Each query is scored by nDCG with the 0–3 relevance grade as gain and a `log2(rank+1)` discount, normalized by the ideal ranking from that query's complete judgments. The score is 100 times the mean over all hidden queries; invalid, timed-out and unanswered queries count as zero. Running faster than the limits earns nothing extra. The whole task scores zero if the build fails or times out, the size limit is exceeded, memory or storage limits are violated, or the initial load or warmup fails.

`/opt/conda/bin/python /task/tools/check_submission.py --submission /app/submission --index-dir /app/dev-index` builds your submission and checks the interface, development relevance and timing on the five development queries; add `--skip-build` to reuse an existing index. It does not reproduce every final check, such as the serving filesystem quota or the unprivileged user. Your trajectory and submitted files will be reviewed for prohibited inputs, precomputed answers and attempts to bypass the resource, timing or grading rules. Legitimate indexes, models and caches built from allowed inputs are fine. The final score is zero if the integrity review rejects the submission.
