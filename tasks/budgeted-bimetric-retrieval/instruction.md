I need to retrieve Wikipedia passages that help answer NQ questions, while limiting how much information comes from an expensive embedding model. Build a search program that finds candidates in the complete collection, decides which documents deserve expensive scoring, and returns up to ten document IDs in relevance order. Improve ranking quality under the fixed time and scoring budgets; you may choose the index, use lexical or vector signals, adapt candidate exploration after seeing scores, and combine signals for the final ranking. You are not given a candidate list.

The supplied collection is a fixed subset of 250,000 BEIR NQ documents in `/task/public/corpus.parquet`, with `_id`, `title`, `text` and `source_id` columns; `source_id` records the original BEIR ID. Row i has ID `doc{i}` and corresponds to row i in `/task/public/cheap.f32`, a row-major little-endian float32 array of shape (250000,384). Use the task-local `_id` in protocol messages, rather than `source_id`. The subset retains every labelled relevant document for the development and test questions and fills the remaining rows by uniform sampling without replacement with seed 20261021. The original FP32 representations are preserved without re-encoding or quantization. These cheap bge-micro-v2 vectors are unit-normalized. `/task/public/config.json` records the dimensions, encoding, fixed asset accounting and frozen grading references B and U. For development, `/task/public/dev-queries.jsonl` supplies 500 NQ training queries with `query_id`, `text` and a `vector` containing 384 finite numbers; `/task/public/dev-qrels.tsv` supplies their labels on this same corpus, using `query-id`, `corpus-id` and `score` columns. Final grading uses all 3452 BEIR NQ test queries and their relevance labels. Those questions, their cheap and expensive query vectors, and labels are isolated at runtime.

The expensive document and query vectors belong to a trusted scoring service. They are unit-normalized float32 SFR-Embedding-Mistral representations with 4096 dimensions. You can request the Euclidean L2 distance from the current query to particular document IDs; distances use float64 accumulation, and smaller is better. You cannot read the private vectors or model weights, substitute a query vector, or ask the expensive representation for full-corpus nearest neighbors. Each query permits at most 20 document scores. A batch of n documents costs n calls, and repeated requests for the same document cost calls again. Reusing a cached score within that query is fine. Your final documents need not all have been scored by this service.

Put an executable `/app/search.sh` and all custom source or dependencies not already provided by the runtime under `/app`. Only `/app` is transferred; packages you install or background processes you start during development are not carried over. You may include parameters learned from permitted public development data. Development artifacts left under `/app` also count against final storage, even though the final index is rebuilt separately. The verifier runs your code as UID 10001, with `/app` read-only and a fresh working directory `/work/runtime`. During construction, store indexes and other prepared files in the supplied index directory or its parent working directory. The first invocation is `/app/search.sh --data-dir /task/public --index-dir /work/runtime/index --mode build`. Rebuild from the supplied public inputs and permitted learned parameters, finish preprocessing, index construction and loading, then write exactly `{"op":"ready"}` as one flushed stdout line and wait for queries. All protocol messages are JSONL, each at most 1 MiB; send diagnostics to stderr.

For each query, stdin supplies `{"op":"query","token":"opaque-token","text":"question","vector":[...]}`. The token is an unpredictable handle for that query, and future questions are not disclosed. To request distances, write a line such as `{"op":"score","token":"opaque-token","doc_ids":["doc0","doc1"]}`. Batches must be nonempty. The reply has the form `{"op":"scores","token":"opaque-token","distances":[0.1,0.2],"used":2,"remaining":18}`, with distances in the requested order. The first request exceeding the budget invalidates the query, even if your program ignores the error. Finish with `{"op":"result","token":"opaque-token","doc_ids":["doc1","doc0"]}`. Use exact, known document ID strings, without duplicates, in the desired ranking order. Return at most ten IDs; an empty list is valid. No numeric result scores are required.

Successful queries reuse the loaded worker, which is suspended along with its descendants between queries. A failed or expired query causes its process family to be killed. Before the next question, the verifier may invoke the same command with `--mode load`, so restore the existing index and emit the ready message again. Initial construction and all subsequent loading together have 3600 seconds. A failed build or reload, or an exhausted startup allowance, invalidates the submission; individual query failures otherwise remain zero-valued entries in the complete test mean.

Final grading provides 16 CPU cores and 32 GiB of total cgroup memory, counting the scorer, your program, descendants and page cache, with swap disabled. Storage is limited to 64 GiB in total, including both sets of fixed vectors, corpus and query data, your submitted files, indexes, caches, temporary files and diagnostics. Immutable preinstalled system software is excluded. The bounded workspace holds the remainder after the actual fixed asset sizes and a 512 MiB diagnostic reserve. Queries run one at a time. Complete-response timing includes query delivery, local retrieval, service work, sorting, output and suspending the process family. The measured time includes use of the supplied precomputed-vector service. Reducing time or calls does not independently earn points.

You have two hours for development. During that stage the main container receives 15 CPU equivalents and 31 GiB, and the separate development scorer receives 1 CPU and 1 GiB, jointly fitting the same 16 CPU and 32 GiB budget; the final verifier can use all 16 CPU cores and 32 GiB together. The same total storage rule applies to both stages. There is no GPU, external network, additional model API or external pretrained model weight access; the expensive model weights are never exposed. Use the supplied text, cheap vectors and public development data. Do not access hidden questions or labels, use precomputed test-answer mappings, tamper with grading or rewards, or bypass the controlled interface to access private vectors. Learning from allowed public development data is permitted. Local Unix IPC and child processes are permitted within the resource limits.

Read `/task/docs/environment.md` and `/task/docs/available_resources.md` for the installed runtime and service. The vector, direct-vector, hybrid and two-round feedback baselines are available under `/task/baseline`. See `/task/docs/available_resources.md` for preparation and invocation. For a development check, run `python /task/tools/evaluate.py --output /app/dev-results.json --limit 20 --command /app/search.sh --data-dir /task/public --index-dir /app/dev-index --mode build`; use `--limit 500` for all development questions. This helper is a diagnostic client, while final resource and process enforcement belongs to the verifier. You can also use `/task/tools/oracle_client.py`: `call('/begin', {'query_id': ...})` starts a timed 20-call session for one public development query, and `call('/score', request)` obtains distances through `/run/oracle/oracle.sock`. Repeated development sessions are allowed. Final verification has no query-reset interface and exposes only the current question.

The ranking metric is BEIR nDCG@10, with the ideal ranking computed from the complete relevance-label set for that question, not just your candidates. Exceeding 20 calls in any measurement, an invalid result, or failing the timing checks below gives that question nDCG zero. Construction or startup failure, memory or storage excess, or an integrity violation makes the final score zero. Let Q be the average nDCG over all 3452 test questions, including failures. B is the highest resource-valid mean from the frozen simple baselines: cheap top-20 then expensive reranking, lexical/vector hybrid top-20 then expensive reranking, direct cheap top-ten, and two-round retrieval with a development-trained tree ranker and expensive-distance feedback. Their implementations and parameters are selected using development data. U is the offline quality of exact full-corpus expensive-vector top-ten retrieval on the same test questions. The displayed score is `100 * clip((Q-B)/(U-B),0,1)`, and the Harbor reward is that score divided by 100. Average the entire test set before applying this mapping: matching B gives zero, reaching or exceeding U gives 100. U is a full-credit reference rather than a theoretical upper bound on relevance, so the actual raw quality is reported if you exceed it.

An independent integrity review checks the trajectory and submitted files for forbidden test-answer mappings, hidden-label use and other stated violations. Missing, failed or malformed review evidence cannot yield a positive reward. Zero expensive-distance or model calls are allowed. General indexes, caches and parameters derived from permitted inputs remain allowed.

Each test query is measured five times in five complete passes over the query set. The index is built once. Before each pass, the verifier starts a fresh load worker and clears its writable scratch directory. Prepared artifacts become read-only after construction; use the supplied TMPDIR for query-time writes. Initial construction and all loads share the 3600-second startup allowance. Each measurement receives a fresh query token and a separate 20-score allowance. The median of the five complete-response times must be at most 2.0 seconds. Each individual measurement has a 3.0-second execution cap. All five results must satisfy the protocol and score budget; otherwise that query scores zero. For a query that passes these checks and the median time limit, its quality is the arithmetic mean of the five nDCG@10 values.

The integrity review runs independently three times. Its reported value is the arithmetic mean of the three binary decisions. A positive task reward requires all three reviews to accept the submission. A missing, failed or malformed review is an evaluation infrastructure failure.
