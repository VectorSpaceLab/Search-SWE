I have a collection whose vectors are already computed, and I need a compact, deployable search system for it. The system prepares an index once, then answers query vectors on a worker with one logical CPU, 512 MiB of memory and a 64 MiB index workspace, returning the top matching corpus items for each query. It must reach at least 95% latency-gated Accuracy@3 on held-out queries, and beyond that, lower tail latency scores higher. Any indexing, storage and retrieval architecture is acceptable within the limits and interfaces below.

The corpus is `/task/data/vectors.f32`: 1,500,000 normalized float32 vectors of dimension 1024. `/task/data/metadata.jsonl` has one row per vector in the same order, and `/task/data/vector_config.json` describes the collection. Public development queries are `/task/data/validation/query_vectors.f32` with `/task/data/validation/query_metadata.jsonl` and `/task/data/validation/vector_config.json`; `/task/data/validation/queries.jsonl` holds the query records and `/task/data/validation/ground_truth.jsonl` their relevance labels. Final evaluation uses 20 held-out query vectors with private relevance judgments, disjoint from the public ones. All supplied data is read-only, and the corpus files remain readable during querying, so they may be used for retrieval and reranking.

Read `/task/docs/environment.md` and `/task/docs/available_resources.md` before implementing. Use only the supplied vectors and task data: no external models, retrieval services or datasets, and no hard-coded or precomputed query-to-result mappings. Implement genuine vector retrieval over the corpus. You have 120 minutes for implementation, validation and debugging. Create and modify submission files only under `/app`.

Development and the final build have 16 CPUs, 512 MiB of memory with no swap, 100 GiB of storage and no GPU. The 512 MiB limit is shared by every process you start, page cache charged to them, and the index workspace itself. Online queries have a single logical CPU shared by the client, any service and all descendants. `/task/index` is a fresh 64 MiB tmpfs in both phases, and it is the only place for build and query artifacts: indexes, lookup tables, executables, logs, sockets, temporary files and caches, measured by logical size. The only exception is the result file at the supplied `--output` path. Do not store generated search state anywhere else. Symbolic links are not allowed in the index workspace.

Submit executable `/app/build.sh` and `/app/run.sh`; supporting code may go in `/app/src` and notes in `/app/README.md`. Verification runs as a non-root user with `/app` read-only, so use the paths passed on the command line. The build is invoked as:

`/app/build.sh --vectors /task/data/vectors.f32 --metadata /task/data/metadata.jsonl --config /task/data/vector_config.json --index-dir /task/index`

It starts from an empty workspace, must derive all corpus-dependent search state from the supplied inputs rather than from prebuilt data shipped in `/app`, and must exit with status 0 within 150 seconds once the index is ready. After the build, every submission process is terminated and POSIX shared-memory files and System V IPC objects are removed, so only the files in the index workspace carry over. The operating-system file cache is not flushed.

Queries are invoked as:

`/app/run.sh --index-dir /task/index --query-vectors /task/data/validation/query_vectors.f32 --query-metadata /task/data/validation/query_metadata.jsonl --query-config /task/data/validation/vector_config.json --output /tmp/results.jsonl --top-k 3`

Process every query in the input and write one result line per query. In final evaluation, `run.sh` is invoked once per hidden query, sequentially, for the 20 queries in a fixed order, with no warmup. Each invocation has 0.5 seconds of wall-clock time, from process creation until the process has exited and its output has been captured, so write the complete output before exiting. The first invocation must load the index from the workspace within that same deadline. `run.sh` may start a service that keeps running and serves later invocations; if an invocation times out, the client is killed but such a service is left running. Every query invocation is launched through `/usr/local/bin/search-swe-query-cpu`, which pins the process tree to one CPU; do not change CPU affinity. To measure representative timings during development, stop any services your build started, then run `/usr/local/bin/search-swe-query-cpu /app/run.sh` followed by the normal arguments.

Each output line has the form `{"query_id":"query-id","results":[{"doc_id":"document-id","score":0.123}]}`, where `query_id` is the input query's identifier. With `--top-k 3`, return exactly three distinct corpus `doc_id` values with finite numeric scores, ordered by descending score, breaking ties by corpus order.

A hidden query passes if its invocation exits successfully, its valid output is captured within 0.5 seconds, and at least one relevant document is among its three results. Let `A` be the fraction of the 20 queries that pass, and `L95` the 19th smallest of the 20 durations in seconds; timeouts and failed launches count as 0.5 seconds, and all other durations are capped at 0.5. If `A < 0.95`, meaning fewer than 19 queries pass, the score is zero. Otherwise the score is `100 * A * min(1, 0.030 / L95)`. The whole task scores zero if the build fails, the workspace limit is exceeded, the memory limit causes an out-of-memory kill, or the retrieval-integrity review fails, or rejects the submission.
