# Incremental Vector Search sources

## Source datasets and usage terms

The 1536-dimensional vectors come from [Qdrant/dbpedia-entities-openai3-text-embedding-3-large-1536-1M](https://huggingface.co/datasets/Qdrant/dbpedia-entities-openai3-text-embedding-3-large-1536-1M/tree/4a9731217921bc476a0f03544f11f22ae4903fa5), revision `4a9731217921bc476a0f03544f11f22ae4903fa5`. Its pinned dataset card declares MIT. The 3072-dimensional vectors come from [Qdrant/dbpedia-entities-openai3-text-embedding-3-large-3072-1M](https://huggingface.co/datasets/Qdrant/dbpedia-entities-openai3-text-embedding-3-large-3072-1M/tree/b2f301648eda4c5dbe659235589c86ffec702581), revision `b2f301648eda4c5dbe659235589c86ffec702581`. Its pinned card declares Apache 2.0. Keep these per-source notices rather than assigning one blanket license to both collections.

The source cards describe embeddings of title plus text from the first million BeIR DBpedia entities, following `KShivendu/dbpedia-entities-openai-1M`. This package redistributes selected numeric embeddings and deterministic array metadata, not the original document text. The card declarations describe the upstream releases; they do not assert unrestricted rights in all underlying source material or model outputs. Copies of the pinned source cards are retained outside the task under `../task_development/incremental-vector-search/provenance/`, relative to the repository root.

## Derivation

The external `task_development/incremental-vector-search/authoring/` archive retains the original twelve immutable Parquet shard references, byte sizes, SHA-256 hashes and data-generation scripts. These are provenance tools only; the task restores the finished files directly. For each dimension, PCG64 seed `260306661` samples 125,000 distinct rows from the concatenated selected shards, and seed `260306660` splits them into 105,000 initial rows, 10,000 future insertions and 10,000 held-out queries. Vector values are cast to little-endian float32 without normalization; corpus order defines IDs. `source_rows.npy` and `derived-manifest.json` preserve the sampled-row identity and output hashes under the external `task_development/incremental-vector-search/data-preparation/` directory. They are authoring records, not runtime data.

The public validation workload is derived exclusively from the initial corpus: 10,000 initial rows, ten batches of 100 insertions and 100 queries. Public validation query rows are excluded from that validation corpus and disjoint from held-out queries. The eight warmup rows are also selected from the initial corpus. This revision preserves the original input array bytes and sampling rules; it changes their directory layout and adds public exact targets.

The prepared layout is `data/corpus/`, `data/validation/` and `tests/data/`. `assets.json` records all 28 finished files with their sizes, hashes and official dataset paths, pinned to revision `13c218a82ae222dc65a4eeb070e4f46602b5cadb`. The standard downloader restores both public and verifier-only inputs directly. These numeric held-out fixtures are hidden from the running agent, not confidential source records. Only public corpus/validation directories are mounted into the agent. Maintenance records and machine-specific timing budgets are excluded from dataset publication. Public validation targets are Top-1000 IDs and squared L2 distances generated with the recorded Faiss direct float32 kernel.

## Runtime-specific targets and budgets

`tests/kernel.py` adapts exact targets to the current numerical runtime using the already prepared float32 arrays. The redundant standalone generation entrypoint is archived with the authoring tools. The cache records the Faiss binary/numeric signature, all three input hashes, shapes, and target hashes. Changed inputs or runtime regenerate the targets rather than reusing labels produced by another numerical kernel. Equal boundary distances are accepted by the grader without adding a numerical tolerance.

`tools/prepare_task.py` is invoked automatically by the evaluation launcher and maintains verified caches under ignored `tests/platform/<cache-key>/`. It measures one full event replay of each exact/PQ reference per collection, then freezes query budgets and the baseline missed-neighbor anchor. Formal submission verification separately uses five replays and median timing gates. These measurements are specific to that machine/allocation/runtime, are not dataset assets, and must not be copied to a different platform. The raw vector arrays and original logarithmic score formula remain fixed across platforms; wall-clock budgets and runtime-dependent reference statistics are regenerated.
