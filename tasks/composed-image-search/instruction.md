A user starts with a photograph and describes a change they want, such as a different arrangement or a different quantity of an object. Build an image search system that finds matching photographs in the supplied gallery while retaining the parts of the reference that the request leaves unchanged.

The gallery is at `/task/data/corpus/`. Each row of `records.jsonl` contains `image_id` and `image_path`; paths are relative to the corpus directory. Gallery images are supplied. Local image and text encoder weights are available at `/task/models/clip/`.

Provide executable `/app/build.sh` and `/app/run.sh` with their supporting files under `/app`. The build interface is `/app/build.sh --corpus /task/data/corpus --index-dir /work/index`. The query interface is `/app/run.sh --index-dir /work/index --queries /work/input/queries.jsonl --output /work/output/results.jsonl`. Honor the supplied paths. Each input JSONL row contains `query_id`, `reference_image_id`, `modification` and `shared_concept`. The reference belongs to the gallery. `shared_concept` provides an additional description when available and can be empty; the reference and modification still define the request.

Return one JSONL row for each request with its unchanged `query_id` and a `results` list of at most 50 distinct gallery images. Each result contains `image_id` and a finite numeric `score`, ordered by nonincreasing score. Exclude the reference image. Write diagnostics to stderr. Public requests and relevance labels are at `/task/data/validation/queries.jsonl` and `/task/data/validation/labels.jsonl`. Labels map each `query_id` to `qrels`, which may contain several matching images. You may use these examples to develop and check the system.

You have two hours, 8 CPU cores, 32 GiB RAM and 100 GiB working storage and one GPU. The build command has 3,600 seconds. The system must handle up to 4,400 requests in two calls of at most 2,200 requests, with an independent 14,400-second allowance for each call. At most 100 candidate images per request may undergo additional query-dependent visual inspection. Corpus-wide global-vector screening and gallery-only preprocessing are allowed. The local model and permitted APIs are available as described in `/task/docs/available_resources.md`; also read `/task/docs/environment.md`.

During verification, build and query commands run as a non-root user. The implementation under `/app` and the supplied inputs are read-only. The passed index directory already exists and is writable, but its parent directory is not writable. Create build files, caches and temporary directories inside that index directory or the supplied `TMPDIR`; do not create sibling directories or rename the index directory itself. The index persists and remains writable across query calls. Write results at the passed output path, whose parent directory is writable. Honor `TMPDIR` and `XDG_CACHE_HOME` rather than writing to `/app` or assuming a writable system temporary directory.

Treat data, models and documentation as read-only. The submitted `/app` files must work in a fresh environment with the supplied inputs, using the passed index and output paths for generated files. Query calls may be repeated after a build. Completed valid JSONL rows remain usable if a call times out; missing or invalid rows are unsuccessful. A command failure other than timeout invalidates that call. Aim to return the requested images near the start of each ranking across the supplied requests.

The integrity review runs independently three times. Its reported value is the arithmetic mean of the three binary decisions. A positive task reward requires all three reviews to accept the submission. A missing, failed or malformed review is an evaluation infrastructure failure.
