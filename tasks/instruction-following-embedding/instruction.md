I need our news-retrieval embedder to respond when the relevance instruction changes while the query stays the same. Our document index was built with the supplied, unchanged E5-large-v2 encoder and cannot be rebuilt, and each tenant gets its own small query adapter on top of the shared base. Please train a LoRA adapter for the query side only. When an instruction is revised to exclude some documents, those documents should move down the ranking, while relevant documents stay near the top under both the original and the revised instruction. The improvement has to hold on all three subsets: Robust04, Core17 and News21.

Read `/task/docs/environment.md` and `/task/docs/available_resources.md` before starting. Everything under `/task` is read-only. The base model is `/task/models/e5-large-v2`. Use only this model, the supplied data and the installed libraries. No external pretrained models, datasets, network services or retrieval endpoints are allowed.

`/task/data/train.jsonl` holds 1,717 training records with `query`, `instruction`, `document`, `label`, `score` and `id` fields. `/task/corpus/{robust04,core17,news21}.jsonl` holds 98,312 passages with `_id`, `title` and `text` fields; the document text is `(title + ' ' + text).strip()`. `/task/public/dev-groups.json` holds 20 validation groups: 10 Robust04, 4 Core17 and 6 News21. Each group has a query, an original and a changed instruction, its 1,000 candidates, and relevance judgments for both versions. Final grading uses 84 hidden groups of the same kind. Paired instructions and related topics are never split between the validation and hidden sides.

All training supervision must come from `train.jsonl`, including any teacher models or derived examples you build from it. You may use the validation groups for evaluation, failure analysis, choosing global hyperparameters, choosing checkpoints, and scalar blending of checkpoints trained on the training set. You may not use their queries, instructions or judgments for gradient training, teacher targets, pseudo-labels, label-aware negative mining or any other weight optimization. Metric code may read validation labels but must not backpropagate through them. Corpus passages may be used as unlabeled text or as document-embedding anchors, as long as no query–passage relevance information is used. These rules apply to every intermediate model that influences the final adapter, and your training code and trajectory will be reviewed for compliance. Do not try to obtain hidden queries, judgments, verifier files or reference solutions.

During training you are free to use full fine-tuning, larger training-only checkpoints initialized from the supplied base, teachers, custom losses and negatives, other input formats or pooling, and multiple forward passes. Only the final LoRA adapter is deployed, and it is evaluated through the fixed serving setup below, which you cannot change.

Serving uses the base tokenizer with normal special tokens and right truncation to 512 tokens. The query input is `query: {query}\nInstruction: {instruction}`, with a real newline before `Instruction:`. The document input is `passage: {text}`, where `{text}` is the combined title and text above. E5 runs in bfloat16 with SDPA. The final hidden states are cast to float32, averaged equally over all non-padding tokens including special tokens, and L2-normalized into 1,024-dimensional vectors. Your adapter is merged into the base for query encoding only; documents are always encoded by the unmodified base. Each query gets a single forward pass, with no test-time adaptation. Candidates are ranked by cosine similarity, and ties keep the original candidate order. Query embeddings must be finite and nonzero; if either instruction version of a group fails, the whole group scores zero.

Put your submission in `/app/submission`. `submission.json` must contain exactly two keys, for example `{"query_checkpoint": "query-checkpoint", "document_checkpoint": "base"}`. `document_checkpoint` must be `"base"`. `query_checkpoint` is either `"base"` or a relative subdirectory of `/app/submission` containing a standard PEFT LoRA `adapter_config.json` and `adapter_model.safetensors`. The total size of all `.json` and `.safetensors` files under `/app/submission` must not exceed 524,288 bytes (512 KiB). Optional Markdown notes do not count toward this limit. Weights must be unquantized FP16, BF16 or FP32. PEFT saves FP32 by default, so check the stored precision and file size. Custom adapter types, `auto_mapping`, `modules_to_save` and `layer_replication` are not supported. Do not include anything else: no code, tokenizer files, `.bin`/`.pt`/pickle files, symlinks, copies of the base model or document vectors. Final evaluation runs as an unprivileged user, so make every submission file world-readable.

Instruction following is measured by p-MRR. Changed documents are those judged relevant under the original instruction but not relevant under the changed one. For each changed document, let `x` and `y` be its 1-based rank under the original and the changed instruction; a changed document missing from the candidates has rank 1,001. Its value is `y/x - 1` if `x >= y`, and `1 - x/y` otherwise, so pushing excluded documents down is positive. Values are averaged over changed documents within each group, then over groups within each subset, on the raw scale from -1 to 1. The objective is the harmonic mean `H = 3 / (1/P_robust04 + 1/P_core17 + 1/P_news21)`, which is 0 unless all three subset values are positive. The untrained base scores `H = 0`; a nonzero score requires positive final p-MRR values on all three subsets.

Retrieval quality must not collapse. For each subset, nDCG@10 (linear gains, ideal DCG from all judgments) must reach at least these floors under the original/changed instruction: Robust04 0.40207235525924456/0.24732655719087798, Core17 0.3167028154626008/0.1541820370950148, News21 0.4020637911913562/0.236479228075062. These are 90% of a query-only E5 reference. If any floor is missed, the score is zero.

You have 120 minutes in total for preprocessing, training, tuning and validation, with 16 CPU cores, 32 GiB RAM, 32 GiB task storage and one A100-SXM4-40GB. Final evaluation allows up to 3,600 seconds for preparation and 1 second per query per instruction version, including encoding, transfer, normalization, candidate scoring and sorting. Work under `/app`, a 28 GiB tmpfs; `/tmp` is a separate 1 GiB tmpfs, and both count against RAM. Checkpoints, vectors and caches count toward storage. When time runs out, processes are stopped and whatever valid submission is in `/app/submission` is graded, so put a valid submission in place early and update it as you improve. Do not modify evaluation files, timing, resource limits or collection.

`python /task/baselines/baseline.py` reproduces the untrained baseline and caches base document vectors under `/app/baseline-cache`. Since the document encoder never changes, you can reuse those vectors for fast validation experiments. `python /task/runtime/evaluate.py --groups /task/public/dev-groups.json --output /app/public-evaluation` runs the full serving pipeline on a prepared submission. It re-encodes the whole corpus and is slow. You can use this command to validate your final submission.
