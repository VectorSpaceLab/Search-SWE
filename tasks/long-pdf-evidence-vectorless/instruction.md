I need to verify interpretations of events in a long novel against the original text. My questions are brief descriptions of a tension, motive, reversal, or relationship, and often do not name the characters. Please build an executable retrieval system that finds a small set of original sentences which, read together, fully support the requested explanation. I will use those sentences to check the interpretation without reading entire retrieved pages. Return evidence only; do not generate an answer. I need a reusable index that can answer later questions after access to the source corpus has been revoked. Do not use embeddings at any stage, including local models, embedding endpoints, precomputed embeddings or text vector representations for retrieval. Lexical indexing, document structure, permitted generation and non-embedding candidate reranking are allowed; no particular architecture is required.

The shared document is the sole PDF in `/task/data/corpus`. Beside it, `sentences.jsonl` supplies a fixed, question-independent inventory of sentence units. Every record has `sentence_id`, `text`, and `pages`, where `pages` lists the 1-based physical PDF pages containing that unit. The inventory normalizes PDF typography and whitespace and defines the output boundaries, including dialogue and sentences crossing pages. You may use any internal parsing, chunking, indexing, or retrieval architecture, but return complete inventory units. Page numbers are provenance and do not determine the score. Use the inventory text when copying evidence; do not truncate, concatenate, paraphrase, or append an explanation to a unit.

Ten public examples are in `/task/data/validation/queries.jsonl`, with reference evidence in `/task/data/validation/golden_answers.jsonl`. Each query is `{"query_id":"opaque-query-id","query":"Question about the novel."}`. Each label has `query_id`, a `requirements` list explaining the information needed, and an `evidence` list of `{"sentence_id":"inventory-id","sentence":"complete inventory text"}` objects. These are sufficient examples, not the only acceptable evidence. The twelve private questions use the same PDF and sentence inventory but different questions and reference evidence. IDs are opaque and independent across splits; query order does not reveal locations. No `target` field is supplied.

Read `/task/docs/environment.md` and `/task/docs/available_resources.md` before implementing. Follow their exact permitted models, providers, endpoints, runtime credential rules, and jailbreak penalties; unlisted resources are not implicitly permitted. Harbor injects the documented API credentials at runtime: never embed credentials in artifacts or an image. The environment has 16 CPUs, 16 GiB RAM, 100 GiB storage, and no GPU. You have 120 minutes for implementation, validation, and debugging. Treat `/task` as read-only and create or modify submission files only under `/app`.

Provide executable `/app/build.sh` and `/app/run.sh`. Optional modules and notes may live in `/app/src` and `/app/README.md`. Preparation invokes `/app/build.sh --corpus /task/data/corpus --index-dir /app/index`. Build all persistent indexes and runtime artifacts in the supplied index directory and return status 0 only when the index is ready. Put all corpus-derived information needed for queries, including sentence text and IDs, inside that directory. Only build may read the source PDF or sentence inventory. Query processing must use the index, input queries and submission code; it must not read the original corpus, copies outside the index or public validation files. This restriction also applies to services and after a verifier restart. Honor all supplied paths: verification stages the same corpus at a different location and may use different index and output paths.

Queries invoke `/app/run.sh --index-dir /app/index --queries /path/to/queries.jsonl --output /path/to/results.jsonl --top-k 5`. Process every supplied query and write exactly one JSON object per query. The verifier invokes this command separately for each private query, with up to five concurrent processes sharing the persistent index. Your internal protocol is unrestricted within this lifecycle and the resource policy.

An output line has exactly the top-level fields `query_id` and `results`, for example `{"query_id":"opaque-query-id","results":[{"sentence_id":"inventory-id","sentence":"complete inventory text"}]}`. Preserve the input query ID. Return zero to five distinct inventory units; `--top-k 5` is a maximum, not a requirement to pad the result. Each item must contain exactly `sentence_id` and `sentence`. No page, score, or generated-answer field is accepted. The text must match the identified unit after Unicode NFKC and whitespace normalization; other wording and punctuation must match. The combined submitted sentence text must not exceed 16,000 characters. Return valid JSON without duplicate keys or duplicate query IDs. Each query's encoded output must also fit within its share of a 64 MiB merged-output allowance, calculated as 64 MiB divided by the number of evaluation queries. Evidence order does not affect grading. An empty evidence list is valid but earns zero.

Only `/app` is transferred to a fresh evaluation environment, where the index is rebuilt from scratch. Public validation files are unavailable. Submission commands run as a non-root user, so dependencies must already be available in the base image or under `/app`. After the build, all build processes are stopped and the source PDF and sentence inventory become unreadable. Queries and any query-time service must use the persisted index without relying on a surviving build process.

The build must finish within 2,400 seconds. Queries run with up to five concurrent invocations, each limited to 900 seconds, within a shared 1,800-second query-phase budget. Queuing does not consume an invocation’s individual allowance, but the shared deadline continues advancing. Queries unfinished or not started when that deadline expires receive zero.

Evidence is sufficient only when the returned original sentences together establish the requested explanation, contrast, reversal, or qualification. A topical match or the right scene alone is insufficient. Alternative original evidence that satisfies the question is accepted; particular reference sentence IDs are not required. The evidence must establish the required facts without borrowing missing information from the reference answer or outside knowledge. Extra relevant or harmless redundant evidence is allowed within the five-unit limit.

The metric is `SentenceEvidenceAccuracy`, measuring complete evidence support averaged across all twelve private queries. Missing, invalid, failed, or timed-out queries contribute zero and stay in that denominator; one failed query does not erase other successful queries. Failure to build or initialize shared verification prevents all queries from scoring. A judge service or parsing failure marks the evaluation invalid and produces no valid accuracy measurement, with a fail-closed final reward of zero; it is reported separately from retrieval mistakes. The report displays 100 times the accuracy before the compliance gate, while reward is on the 0–1 scale. A separate trajectory audit checks resource and task compliance. Only a valid binary pass preserves reward; a failed, missing, malformed, rejected or timed-out audit sets final reward to zero.

Build genuine retrieval over the supplied document. Do not use hidden labels, hard-coded query-to-location mappings, precomputed query-to-answer mappings or answer files, external datasets containing evaluation judgments, or external search or answer services supplying evidence locations or evaluation answers. The documented generation and retrieval APIs may assist your pipeline only within their stated policy. Aim to maximize complete evidence support on unseen questions, rather than similarity to the public reference IDs.
